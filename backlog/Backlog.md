## Feature Backlog

### Version 0.1 — Engine, editor, contribution path

Mapping to the development document: T1 = `0.1.a`, T2 = `0.1.b`, T3 = `0.1.c`, T4/T4b = `0.1.d`.

- [ ] **0.1.d — Catalog: tariff database client and signed catalog packages** *(0.1.c done; re-cut 2026-10-29 after the business-model concept of 2026-10-28; legal questions assumed settled for planning, the legal review item stays open before anything is opened to users)*
  - **Model:** two databases. The *free database* holds user entries, unchecked, with the status `reliable` earned by use (a tariff version used by at least two installations within 12 months, the creator counts). The *verified database* holds only tariffs we checked, kept current, shipped as a signed package by subscription. The GitHub-issue contribution route is dropped, and contributions earn no reward. Edibert keeps format, package check and client public; the review workflow, the verified data, the signing key and the server are private and not part of this repository
  - **Builds on Earnie *Edibert P8* (decided 2026-10-28, Earnie `docs/dev/edibert-integration.md` § P8):** the public Earnie catalog (`tariffs.json`, `grid_fees.json`) is a frozen seed and the start of the verified database; new entries only through this channel. Catalog packages must bring the monthly rates of the reference curves; a package import must not overwrite monthly rows a user entered without telling
  - **Docs to the two-database model** (concept section 7): done 2026-10-31 in `catalog/README.md`, `README.md` / `README.de.md` and `CONTRIBUTING.md` (free database with `reliable` by use, verified database by subscription, no access by contribution, no GitHub-issue route)
  - **Status (2026-10-29):** P1–P6 and the P7 client done ([Erledigt](Backlog-Erledigt.md)); open: the P7 server and the P7 client follow-ups below, the docs bullet above, and the first real signing key in `edibert.package.TRUSTED_KEYS` (generated and kept privately)
  - **Note (2026-10-30):** first signing key `edibert-2026-1` built into `TRUSTED_KEYS`, released as `0.1.10`; the server pins it and builds packages offline. Open on the client side: the P7 client follow-ups below (package download from the editor sidebar among them)
  - **Plan (2026-10-31):** S1 docs (done) → S2 exchange in the publisher loop (done) (daily `report` / `status`, package check and import without conflicts, status block in the MQTT attributes) → S3 editor: status display and package download from the sidebar → release → S4 Earnie: own consent and `ExchangeConfig` at the pin bump
  - **Order:** P1 → P2 → P3 → P4 → P5 is the verified-database path (acceptance: reference curves and one quarter of price changes reach users without editing `tariffs.json` by hand). P6 can run in parallel. P7 needs the exchange contract and the server
  - **Catalog P1 — tariff identity and version:** `tariff_identity(tariff)` gives a stable database ID from land, supplier, product, `area_id` (grid fees only) and direction. `tariff_version(tariff)` is a SHA-256 over the price-relevant fields in canonical JSON (sorted keys, normalised numbers; without `label`, `$comment`, `source`, `last_verified`, `behavior_notes`). Tests: the hash is stable under key order and comments and changes with every price change
  - **Catalog P2 — tariffs with validity versions** (prerequisite; takes over the `0.+1` item *Tariffs that change over time*): several entries with the same ID and `valid_from` / `valid_to` on whole days, no overlap, a date without an entry is an error, never skipped silently (same pattern as `capacity_charges`). Schema, spec sections 2a and 4a. Decided during implementation: `tariff_format` stays 1 (the fields are additive and optional, spec section 2a), so no migration
  - **Catalog P3 — origin on the user tariff:** `db_ref` (`database` = `free` / `verified`, `id`, `version`, `hash`), set on "copy from catalog"; the editor shows "differs from version X" when the hash no longer matches
  - **Catalog P4 — signed catalog package, format and check:** one file with a manifest (`package_format`, `database`, `issued_at`, `valid_until`, `tariff_format`, `key_id`, hashes of the content files) and the content (`tariffs.json`, `grid_fees.json` with the monthly rates of the reference curves), plus a signature checked offline. Proposal: Ed25519 via `cryptography`, public keys shipped in Edibert as a list by `key_id` so a key can be rotated (alternative named in the concept: Cosign/Sigstore). New errors `PACKAGE_SIGNATURE_INVALID`, `PACKAGE_KEY_UNKNOWN`, `PACKAGE_FORMAT_UNSUPPORTED`, `PACKAGE_CONTENT_MISMATCH`; `PACKAGE_EXPIRED` is a warning only, because the last received package may be used after a subscription ends. Edibert only verifies; signing runs in the private workflow, tests use a test key
  - **Catalog P5 — package import:** `package_import_plan(...)` lists new, changed and removed tariffs and the monthly rows that differ from local entries; such a conflict is never overwritten silently, the caller decides per conflict or the import fails. Applying replaces the catalog files atomically; `user_tariffs.json` stays untouched. CLI `python -m edibert package verify|import`, import dialog with preview in the editor, texts in both catalogs, spec and user manual (en, de)
  - **Catalog P6 — sharing client** (payload and UI need no server): `contribution_payload(tariff)` takes only whitelisted fields (no free text, no `behavior_notes`, no meter or consumption data); `individual` tariffs are always refused. Preview of the exact content before the first send, every tariff can be left out. The default comes from the embedding program as a required parameter of `ui/embed.py`: stand-alone Edibert shares by default, Earnie only after opt-in (concept decision 2026-10-29); a missing value is an error, never a silent default. Transport through a replaceable adapter; without a configured endpoint it stays off and says so
  - **Catalog P7 — exchange with the server** (contract first, as public spec `docs/spec/catalog-exchange.md`, analogous to Earnie `docs/workflow/usage-ping.md`). Principle: Edibert always computes locally and offline; the server only delivers and counts, so an outage never changes a price; exchange runs beside the calculation, with a hard off switch by environment variable. Five routes:
    - **Load package** (server → local): `GET /edibert/v1/packages/{free|verified}/latest`, `verified` with `Authorization: Bearer <access key>`; the file goes through P4 and P5. Weekly or when `valid_until` comes near; a manual download and import works the same way
    - **Submit tariff** (local → server): `POST /edibert/v1/tariffs` with the P6 payload, identity and version hash, without any installation ID; answer: database ID, version, `accepted` / `duplicate` / `rejected` with a code; the client then sets `db_ref`
    - **Report use** (local → server, daily): per used tariff version `{db_id, version, pseudonym}` with `pseudonym = HMAC(install_secret, db_id)` computed **on the client**; the secret never leaves the installation, so the server cannot link the tariffs of one installation. Not through Earnie's UsagePing, which carries the installation ID; a call of its own with its own consent in Earnie. One request per tariff with random delay against linking by connection (decide whether needed)
    - **Query status** (daily): `POST /edibert/v1/status` with a list of `{db_id, version}`, without any ID; per entry the newest version with `valid_from`, `reliable` and counters. Shown in the UI, as Home Assistant sensor attribute and in the MQTT topic
    - **Access key:** issued by the server after checking the subscription or Earnie Companion Cloud; stored locally as a secret
    - **Decided 2026-10-29:** usage reports go one request per tariff at a random time of the day, and the server keeps no client IP for `usage` and `status` (also not in the Caddy access log); access keys come from a server CLI until a payment provider is chosen (no webhook yet); server framework FastAPI + uvicorn
    - **Client done (2026-10-29):** contract `docs/spec/catalog-exchange.md`, `edibert.exchange`, CLI `exchange fetch|status|report`, share section sends through the server ([Erledigt](Backlog-Erledigt.md))
    - [ ] **Server** in `earnie-server` against the contract (FastAPI, SQLite, access-key and moderation CLI, systemd + Caddy route without IP log for `usage` / `status`); own session, start from the desktop app
    - [ ] **Client follow-ups:** daily `report` / `status` and package check inside the publisher loop (today: CLI run by a timer); status shown in the editor, as Home Assistant attribute and in the MQTT topic; package download from the editor sidebar; Earnie: own consent and `ExchangeConfig` at the pin bump (no transport without consent)
      - **Done (2026-10-31, S2):** `edibert.publish.exchange_jobs`: block `exchange` in `publish.json` (`report_use`, `status`, `packages`, all required; no block = nothing sent; `EDIBERT_EXCHANGE_OFF=1` still wins). Reports at random times per day, status once a day, package once a week or before `valid_until`; verified with an access key, else free, a verified catalog is never replaced by a free package. Import only without conflicts and without removing a published tariff, else `PACKAGE_HELD_*` warning and the editor decides; the publisher reloads its tariffs after an import. State in `exchange_state.json`; failures give `EXCHANGE_JOB_FAILED` and a retry after an hour, never an offline tariff. Attribute `catalog` per tariff (HA attribute and MQTT topic). Spec `docs/spec/publishing.md`, user manual `publishing.md` (en, de), tests `tests/test_publish_exchange.py`
      - Open: status in the editor and package download from the editor sidebar (S3), Earnie consent and `ExchangeConfig` at the pin bump (S4)
  - **Server side (private, not in this repository; proposal):** a process of its own next to the existing receivers behind the same reverse proxy, with SQLite (tariffs, versions, pseudonyms with last report date, moderation state, hashed access keys with expiry), a small web framework instead of the standard library (routing, auth, webhooks), packages as static files with the access key checked before delivery, a payment webhook, moderation first as a server CLI, rate limits. **The signing key never lives on the server**: it only holds signed files, so a compromised server cannot ship packages Edibert accepts
  - **Note:** Edibert and the catalogue are free — donations are highly welcome; regular reminders may appear on running installations
  - **Note:** Use GitHub issues if a concrete tariff can't be modeled with the existing version
- [ ] **0.1.d2 — Grid areas: complete grid-fee model and operator path** *(decided 2026-10-31; spec sections 5a and 5b, Earnie development document "Benutzertarife" kept consistent)*
  - **Decided:** the grid base fee per year belongs to the grid area, not to the supplier tariff. Today an area has only the work price (`base_cent_kwh`), rules and `capacity_charges`; the fixed charge sits in every tariff as `grid_monthly_fee_eur` and has to be typed per tariff
  - **Gap found on AT-VBG** (seed catalog `grid_fees.json`, source note says "not checked against the price sheet"; network operator price sheet valid from 2026-01-01, Netzebene 7): the work price 4.96 / 2.84 ct/kWh and the SNAP window (`AT_NE7`, 20 % off, 3.968 instead of the published 3.97 ct/kWh) are there; missing: grid base fee 54.00 EUR/year (unmetered power), grid loss charge 0.393 ct/kWh, renewables contribution on work 0.583 / 0.364 ct/kWh plus 0.037 ct/kWh on grid loss, renewables flat fee 19.02 EUR per metering point and year; for metered power the power price per kW and year is not modeled at all
  - [ ] **Format:** per area a fixed yearly amount by metering type, and further per-kWh components next to the work price, each with `id` and `label`. Components stay separate because rules such as SNAP reduce only the work price, not the grid loss charge or the levies. Levies set nationally per Netzebene (renewables contribution and flat fee) should be defined once, like `rule_sets`, not copied into every area. Decide: what happens to the tariff field `grid_monthly_fee_eur` (keep for supplier-billed grid fees, or migrate), and whether `tariff_format` changes
  - [ ] **Engine and output:** work price plus components in the slot price (`grid_cent`, with a breakdown in `PriceResult`), the fixed yearly amount as a separate block like the capacity charge (never folded into ct/kWh); `grid_area_version` covers the new fields; invoice check and preview show them
  - [ ] **Data:** check all 14 AT areas against the network operators' price sheets 2026 and complete them (corrections to the seed are allowed under Earnie *Edibert P8*); SNAP as published absolute values per area where the sheet differs from the flat 20 %
  - [ ] **Operator path:** a way for the database operator to create and edit grid areas (an editor view for grid areas with the same checks as on load, or a validated file) and to put them into catalog packages without editing the frozen seed
  - [ ] **Free catalog for grid areas** (decided 2026-10-31: as important as for tariffs, same mechanism as `0.1.d` Catalog P1–P7): users share their own grid area (own values in the grid-fee section, with land, regions, network operator, metering types, components and time windows) to the free database; it reaches other users in the free package and earns `reliable` by use like a tariff
    - Identity and version: `grid_area_identity` / `grid_area_version` exist (`<LAND>/grid/<id>`); the version covers rule set, components and fixed amounts of the new format
    - Origin: `db_ref` on the user grid area, set on "copy from catalog"; the grid-fee section shows "differs from version X" as for tariffs (P3)
    - Sharing client: a grid-area contribution payload with a whitelist (no free text, no meter or consumption data), shown in the share section next to the tariffs with the same preview, opt-out per entry and the share default of the host (P6)
    - Exchange contract (`docs/spec/catalog-exchange.md`): submit route for grid areas (or `direction: "grid"` on the tariff route), `based_on`, the same answer codes; use reports and status queries cover the chosen grid area like the used tariffs (P7)
    - Packages: shared grid areas approved by moderation go into `grid_fees.json` of the free package; the import keeps a user's own area untouched (P5)
  - [ ] **Area choice in the stand-alone editor** (decided 2026-10-31): today the editor knows only its own grid fee (`user_house`, `house.json`); grid areas from an imported catalog package cannot be selected, so neither the editor preview nor the publisher uses them. The grid-fee section in the main area offers the catalog areas that match the house land and region, or own values; when no catalog area matches, it says so and asks the user to enter the values. Areas need a `regions` field for this (a federal state can hold several areas, e.g. a city operator or Kleinwalsertal next to the state operator); metering type and quarter-hour meter come from the house capabilities. `house.json` stores the chosen area ID; publisher and preview resolve it like Earnie's `netznutzung`
  - **Note:** Earnie consumes the grid fee (house profile, SE invoice); it follows in its own step after the Edibert release. Its own work price ("Eigener Arbeitspreis") has no time windows while Edibert's own grid fee has; align both
